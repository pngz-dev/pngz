pngz Image Format Specification

Version 0.1 (draft)
Status: Pre-standardization

1. Introduction

pngz is a lossless image format derived from PNG's design. It uses PNG's five row filters for image-aware preprocessing and Zstandard (RFC 8878) for entropy coding. It adds optional trained dictionaries for small-file compression and a compact binary-alpha representation.

pngz files use the extension .pngz and the media type image/pngz.

pngz is not PNG. Files are not interoperable in either direction.

2. Conventions

· All multi-byte integer fields in pngz chunks are big-endian.
· Byte offsets are zero-based.
· "MUST", "SHOULD", "MAY" are per RFC 2119.
· u8, u16, u32 denote unsigned 8/16/32-bit integers.
· Hex bytes are written 0xNN.
· "pixel" means one color tuple as defined by color_type.

3. File Structure
   [8-byte signature]
   [IHDR chunk]
   [PLTE chunk]        optional, only for color_type 3
   [ALPH chunk]        optional, only when FLAG_ALPH is set
   [IDAT chunk]        one or more
   [IEND chunk]

Chunks MUST appear in the order above. IHDR MUST be first. IEND MUST be last. PLTE and ALPH, if present, MUST precede the first IDAT. All IDAT chunks MUST be consecutive with no intervening chunks.

pngz has no interlace field and no interlacing modes. All images are stored in a single progressive pass, top to bottom, left to right.

4. Signature

The file begins with exactly 8 bytes:

Offset Byte Purpose
0 0x89 High bit set; detects 7-bit stripping
1 0x50 ASCII 'P'
2 0x4E ASCII 'N'
3 0x47 ASCII 'G'
4 0x7A ASCII 'z' — pngz marker
5 0x0D CR; detects CRLF translation
6 0x0A LF; detects line-ending conversion
7 0x1A DOS EOF; detects DOS-style truncation

A decoder MUST verify all 8 bytes before parsing any chunk.

5. Chunk Layout
   [length: u32][type: 4 bytes][data: length bytes][crc: u32]

· length — size of data in bytes. MUST NOT exceed 268435456.
· type — 4 ASCII letters A–Z or a–z. Uppercase first byte = critical. Lowercase first byte = ancillary.
· data — payload.
· crc — CRC-32 (IEEE 802.3, polynomial 0xEDB88320) over type || data. MUST be verified before processing data.

A decoder MUST reject unknown critical chunks and MAY ignore unknown ancillary chunks.

6. IHDR Chunk

Type: IHDR (critical)
Chunk length: 16. Total on disk: 12 + 16 = 28 bytes.

Offset Size Field Meaning
0 4 width Image width, u32, > 0
4 4 height Image height, u32, > 0
8 1 bit_depth Bits per sample (see section 8)
9 1 color_type Color type (see section 8)
10 1 flags Bit flags (see section 7)
11 1 dict_mode Dictionary mode (see section 12)
12 4 dict_hash FNV-1a 32-bit hash (see section 12)

Constraints:

· width in 1..16384 inclusive.
· height in 1..16384 inclusive.
· width * height MUST NOT exceed 67108864.
· IHDR MUST appear exactly once and be the first chunk.
· There are no reserved bytes in IHDR. All 16 bytes are defined.

7. IHDR Flags Byte

Bit Name Meaning
0 FLAG_ALPH 1 = ALPH chunk present
1 FLAG_RCT 1 = reversible color transform applied
2 FLAG_RAW 1 = IDAT is raw filtered bytes
3-7 reserved MUST be 0

A decoder MUST reject any file with non-zero reserved bits.

Constraints:

· FLAG_ALPH MAY be set only when color_type == 2.
· FLAG_RCT MAY be set only when color_type == 2 or color_type == 6, and only when bit_depth == 8.
· FLAG_RAW MUST NOT be set when dict_mode == 1.

8. Color Types and Bit Depths

color_type Name Channels Valid bit depths Bytes/pixel
0 Grayscale 1 8 only 1
2 RGB 3 8 only 3
3 Palette 1 index 1, 2, 4, 8 see section 9
4 Grayscale+alpha 2 8 only 2
6 RGBA 4 8 only 4

Any other color_type MUST be rejected. Any bit_depth other than those listed MUST be rejected. In particular, 1-bit and 2-bit grayscale are NOT supported; images that would use them MUST instead use the palette path with color_type == 3.

Sample layout within a pixel:

· Grayscale: [Y]
· RGB: [R][G][B]
· Palette: 1 index per pixel, bit-packed per section 9
· Grayscale+alpha: [Y][A]
· RGBA: [R][G][B][A]

Samples are 8-bit unsigned integers in the range 0..255.

12. Dictionary Mode

Value Name Meaning
0 None No dictionary used; dict_hash MUST be 0
1 Reference Zstandard dictionary used; dict_hash set

When dict_mode == 1:

· The IDAT payload is exactly one Zstandard frame compressed with a dictionary (see section 15).
· dict_hash is the FNV-1a 32-bit hash of the dictionary bytes:
  uint32_t hash = 2166136261u;
  for (size_t i = 0; i < dict_size; i++) {
  hash ^= dict[i];
  hash *= 16777619u;
  }
· A decoder MUST have a dictionary whose hash matches dict_hash.
· If the dictionary is missing or its hash differs, the decoder MUST reject the file.
· dict_mode == 1 with FLAG_RAW set is invalid and MUST be rejected.

13. PLTE Chunk

Type: PLTE (critical)
Present only when color_type == 3. MUST precede the first IDAT.

Data layout: a sequence of RGBA entries, 4 bytes each:

Constraints:

· Length MUST be a multiple of 4.
· Length MUST be in the range 4..1024 inclusive (1..256 entries).
· Entries MUST NOT exceed 2^bit_depth:
  · bit_depth 1 -> max 2 entries
  · bit_depth 2 -> max 4 entries
  · bit_depth 4 -> max 16 entries
  · bit_depth 8 -> max 256 entries

A decoder MUST reject any index greater than or equal to the number of PLTE entries.

14. ALPH Chunk

Type: ALPH (critical)
Present only when FLAG_ALPH is set. MUST precede the first IDAT.

Data layout: a bit-packed binary alpha mask, MSB-first, row-major.

the bit is (mask[p >> 3] >> (7 - (p & 7))) & 1. Pixel (0,0) is bit 7 of byte 0.

Bit value:

· 1 -> pixel fully opaque (alpha = 255)

When decoding, color_type is 2 (RGB) and the ALPH mask supplies the alpha channel, producing RGBA output.

15.1 Multi-IDAT Semantics

The data fields of all IDAT chunks MUST be concatenated in file order into a single byte stream. A Zstandard frame MAY span IDAT boundaries. A decoder MUST NOT interpret each IDAT chunk independently. CRC-32 of each IDAT chunk MUST be verified individually before concatenation.

15.2 When FLAG_RAW is clear (compressed)

The concatenated IDAT byte stream MUST be exactly one Zstandard frame as defined in RFC 8878 with the following parameters:

· Frame magic number: 28 B5 2F FD (4 bytes).
· Frame Header Descriptor: contentSizeFlag MUST be 0.
· Frame Header Descriptor: checksumFlag MUST be 0.
· Frame Header Descriptor: dictIDFlag MUST be 0.
· Frame Header Descriptor: singleSegmentFlag MUST be 0.
· Window Descriptor: present; windowLog MUST be in 10..27.
· No skippable frames.
· No multiple frames.
· No trailing bytes after the frame.

If dict_mode == 1, decompression MUST use the referenced dictionary.

The decompressed output MUST be exactly decoded_size bytes. If not, the decoder MUST reject the file.

15.3 When FLAG_RAW is set

The concatenated IDAT byte stream MUST be exactly the raw filtered byte sequence of length decoded_size. The decoder MUST NOT attempt to decompress. If the concatenated length does not equal decoded_size, the decoder MUST reject the file.

16. IEND Chunk

Type: IEND (critical)
Length MUST be 0.

On disk:

The CRC is always 0xAE426082. IEND MUST appear exactly once and be the last chunk. No bytes may follow IEND.

17. Decoding Algorithm
18. Verify the 8-byte signature.
19. Parse chunks sequentially:
    · Verify each chunk's CRC before using its data.
    · Enforce length <= 268435456.
    · Enforce chunk type is 4 ASCII letters.
    · Reject unknown critical chunks.
    · Enforce IHDR first, IEND last, IDAT consecutive.
20. Validate IHDR per sections 6, 7, 8.
21. If color_type == 3, verify PLTE is present and valid.
22. If FLAG_ALPH, verify ALPH is present and exactly ceil(width * height / 8) bytes.
23. Concatenate all IDAT data.
24. Compute decoded_size. Reject if > 536870912.
25. If FLAG_RAW, use bytes directly. Otherwise decompress per section 15.2.
26. For each row:
    · Read filter_type. Reject values > 4.
    · Unfilter using the previous reconstructed row and current row.
    · Write the reconstructed row to the output plane.
27. If color_type == 3, expand indices to RGBA via PLTE.
28. If FLAG_RCT, reverse the color transform.
29. If FLAG_ALPH, combine the RGB plane with the ALPH mask.
30. Output RGBA pixel data, width * height * 4 bytes, row-major.
31. Encoding Considerations

pngz decoders accept any byte stream satisfying sections 1–17. Encoders have freedom in how they produce that stream. Two encoders may produce different bytes for the same input; both are valid.

An encoder SHOULD:

1. Analyze pixels: count distinct RGBA values, detect grayscale, detect binary alpha.
2. Build candidate encodings: palette first-seen, palette frequency-ordered, grayscale, grayscale+alpha, RGB, RGB+ALPH, RGBA, and RCT variants where valid.
3. For each candidate, build the raw stream, apply RCT if applicable, filter each row, compress with Zstandard, and compute total size. If compressed size is not smaller than filtered size, store raw with FLAG_RAW set.
4. Select the smallest candidate.
5. Emit the file.

An encoder SHOULD default to dict_mode == 0. Dictionary use is opt-in.

An encoder SHOULD set ZSTD_c_contentSizeFlag = 0, ZSTD_c_checksumFlag = 0, and ZSTD_c_dictIDFlag = 0.

20. Security Considerations

A decoder MUST:

· Verify the 8-byte signature before any further parsing.
· Verify CRC-32 of every chunk before using its data.
· Enforce width, height, and width*height limits before allocating.
· Enforce length <= MAX_CHUNK_BYTES on every chunk.
· Reject unknown critical chunks.
· Reject invalid color_type or bit_depth values.
· Reject non-zero reserved flag bits.
· Reject out-of-range palette indices.
· Reject palette images without a PLTE chunk.
· Reject ALPH chunk length mismatch.
· Reject non-zero padding bits in palette rows or the ALPH mask.
· Reject dictionary-reference files when the dictionary is absent or its hash does not match.
· Reject files whose concatenated IDAT does not decode to exactly decoded_size bytes.

A decoder MUST NOT allocate memory proportional to unvalidated values from the file header.
